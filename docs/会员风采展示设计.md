## 三、核心规则

### 3.1 图片压缩（重点）

**设计取舍**：不采用「按文件大小压缩到某个百分比」——这种方式对纹理复杂的图会糊、对纯色图又浪费。采用**统一压缩参数**＝所有图片走同一套缩放与编码规则，保证观感一致、可预期。

| 项 | 值 | 说明 |
| --- | --- | --- |
| 输入格式 | `image/jpeg` / `image/png` / `image/webp` | 校验**文件魔数**，不信任 Content-Type |
| 原图大小上限 | **20 MB** | 超过直接拒绝，不再进入压缩流程 |
| 原图像素上限 | 4000 万像素 | 防 decompression bomb |
| 统一输出格式 | **JPEG（sRGB）** | 重编码去掉 EXIF/GPS/ICC，避免隐私泄漏 |
| 统一长边 | **1920 px** | 等比缩放（LANCZOS 类高质量重采样），短边按比例 |
| 统一质量 | **Q = 0.82** | 首个压缩档位 |
| 压缩后上限 | **1 MB（1,048,576 B）** | 硬性红线 |
| 缩略图 | 长边 640 px，≤ 150 KB | 广场瀑布流用，详情用大图 |
| 清晰度下限 | 长边 ≥ 1280 px，质量 ≥ 0.70 | 低于此不再降质，直接拒绝，**保证能看清** |

**压缩降级链**（后端为准，前端预压缩只是省流量）：

```
1. 校验：魔数 / MIME / 原图 ≤20MB / 像素 ≤4000万 / 尺寸合法
2. 等比缩放至长边 1920 → 转 JPEG Q0.82（去 EXIF）
3. 若 > 1MB：质量依次 0.78 → 0.74 → 0.70 重新编码
4. 若仍 > 1MB：长边降到 1600 → 1280，每个尺寸重复步骤 3
5. 仍 > 1MB（或已达清晰度下限）→ 拒绝，提示「图片纹理过密」
6. 通过后：生成 640px 缩略图 → 两文件落盘 → 写库
```

**前端预处理**：用 `canvas` 先等比缩到长边 1920 并转 JPEG 再上传，减少上行流量；iPhone 的 HEIC 由浏览器解码后转 JPEG。**后端必须完整重做一遍校验与压缩**，不能信任前端结果。

### 3.2 拒绝与提示

| 场景 | 前端提示 | 是否占额度 |
| --- | --- | --- |
| 非图片 / 格式不支持 | 「仅支持 JPG / PNG / WebP 图片，本期不支持视频」 | 否 |
| 原图 > 20 MB | 「图片过大（26.4 MB），超过 20 MB 上限，请换一张」 | 否 |
| 像素 > 4000 万 | 「图片分辨率过高，请裁切后重试」 | 否 |
| 压缩后仍 > 1 MB | 「压缩后仍超过 1 MB，为保证清晰度已停止压缩，请换一张」 | 否 |
| 今日额度用尽 | 「今日 4 张已用完，每日 0 点重置」 | — |
| 文件校验失败（未落库） | — | **否** |
| 上传成功（含审核中/已发布/已驳回/已删除） | — | **是** |

> 口径：**一旦成功落库就占当日额度，审核驳回、主动删除都不返还**，避免「发了删、删了发」刷屏。若以后要改成「驳回返还」，只需在驳回时把计数表 `-1`。

### 3.3 每日 4 张

- 自然日按 **Asia/Shanghai 0 点**切分（与现有定时任务时区一致）。
- 计数维度：`member_id + upload_day`。
- **并发强约束**：不依赖 Redis（第一版无 Redis），用独立计数表 + 单条原子 SQL：

```
INSERT INTO moment_daily_quota(member_id, upload_day, used_count)
VALUES (?, ?, 1)
ON DUPLICATE KEY UPDATE used_count = used_count + 1
```
  执行前用 `WHERE used_count < daily_limit` 或检查 `affected rows`；更稳妥写法是把限额判断放进 `UPDATE ... WHERE used_count < :limit`，受影响行数为 0 即额度用尽。整段与落库放在同一事务。
- 前端 `GET /api/moments/quota` 展示 `2/4` 与四个圆点，仅做展示，**以后端判定为准**。

### 3.4 评论与回复

采用**两层结构**（评论 + 楼中楼），不做无限嵌套：

| 字段 | 一级评论 | 回复 |
| --- | --- | --- |
| `parent_id` | NULL | 被回复的那条评论 id |
| `root_id` | NULL（自身即楼） | 所属一级评论 id |
| `reply_to_user_id` | NULL | 被回复人 user_id |

- 对「回复」再回复时，**仍挂到同一个 `root_id`** 下，展示为 `A 回复 B：内容`，不产生第三层缩进。
- 列表按 `root_id` 分组，楼内按时间升序；一级评论按时间倒序。
- 内容上限 **200 字**，纯文本存储，前端用 `v-text` 渲染（禁 `v-html`）。
- 删除为**软删**（`status=DELETED`，内容替换为「该评论已删除」），保留楼中楼结构与回复关系；图片被删除时其下评论一并软删。
- 空内容、纯空白、超长、1 秒内连发由后端校验（可选 `comment-max-per-minute`）。

### 3.5 审核（可配置）

- `app.moments.need-review = true`：**先审后发**，新图状态 `PENDING`，仅作者本人与管理员可见；管理员通过后 `APPROVED` 才进广场。
- 设为 `false`：上传即 `APPROVED`，管理端审核页隐藏。
- 驳回需填理由 `reject_reason`，会员端「我的发布」可见。
- 审核动作写 `operation_log`（沿用现有表）。

## 四、数据模型（仅设计，尚未加入 `schema.sql`）

### 4.1 改造现有 `media` 表

原 V1 设计：`media(id, member_id, type, url, size, duration, status)`。本期扩展为：

```sql
CREATE TABLE IF NOT EXISTS media (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id      BIGINT       NOT NULL COMMENT '发布会员',
    author_role    VARCHAR(20)  NOT NULL DEFAULT 'MEMBER',
    title          VARCHAR(200) NULL COMMENT '配文，≤200 字',
    type           VARCHAR(10)  NOT NULL DEFAULT 'IMAGE' COMMENT '本期固定 IMAGE',
    url            VARCHAR(255) NOT NULL COMMENT '大图相对路径',
    thumb_url      VARCHAR(255) NOT NULL COMMENT '缩略图相对路径',
    width          INT          NOT NULL,
    height         INT          NOT NULL,
    source_size    BIGINT       NOT NULL COMMENT '原图字节',
    output_size    BIGINT       NOT NULL COMMENT '压缩后字节',
    source_format  VARCHAR(10)  NULL COMMENT 'HEIC/JPEG/PNG/WEBP',
    upload_day     DATE         NOT NULL COMMENT 'Asia/Shanghai 自然日',
    status         VARCHAR(20)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/APPROVED/REJECTED/DELETED',
    reject_reason  VARCHAR(200) NULL,
    review_by      BIGINT       NULL,
    review_at      DATETIME     NULL,
    comment_count  INT          NOT NULL DEFAULT 0,
    duration       INT          NULL COMMENT '本期不用，保留 NULL',
    create_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    KEY idx_status_day (status, upload_day, id),
    KEY idx_member_day (member_id, upload_day)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '会员风采图片';
```

### 4.2 新增评论表

```sql
CREATE TABLE IF NOT EXISTS media_comment (
    id                BIGINT AUTO_INCREMENT PRIMARY KEY,
    media_id          BIGINT       NOT NULL,
    user_id           BIGINT       NOT NULL,
    author_role       VARCHAR(20)  NOT NULL,
    author_name       VARCHAR(30)  NOT NULL COMMENT '冗余展示名，避免连表',
    root_id           BIGINT       NULL COMMENT '一级评论 id；一级评论为 NULL',
    parent_id         BIGINT       NULL COMMENT '被回复的评论 id',
    reply_to_user_id  BIGINT       NULL,
    reply_to_name     VARCHAR(30)  NULL,
    content           VARCHAR(200) NOT NULL,
    status            VARCHAR(20)  NOT NULL DEFAULT 'NORMAL' COMMENT 'NORMAL/DELETED',
    create_time       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    KEY idx_media_root (media_id, root_id, id),
    KEY idx_user_time (user_id, create_time)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '风采评论/回复';
```

> 冗余 `author_name` / `reply_to_name`：改名后历史评论仍显示当时名称，且列表免连表。

### 4.3 新增每日额度表

```sql
CREATE TABLE IF NOT EXISTS moment_daily_quota (
    member_id   BIGINT   NOT NULL,
    upload_day  DATE     NOT NULL,
    used_count  TINYINT  NOT NULL DEFAULT 0,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (member_id, upload_day)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT '风采每日额度计数';
```

## 六、配置项（`application.yml`）

```yaml
app:
  moments:
    enabled: true
    need-review: true                 # 是否先审后发；false 则上传即展示
    upload-dir: /opt/fitness/upload/moments
    url-prefix: /upload/moments
    accept-types:                     # MIME 白名单（后端按魔数复核）
      - image/jpeg
      - image/png
      - image/webp
    max-source-bytes: 20971520        # 原图 > 20 MB 直接拒绝
    max-source-pixels: 40000000       # 4000 万像素，防图片炸弹
    max-edge: 1920                    # 统一长边
    min-edge: 1280                    # 清晰度下限，不再缩小
    thumb-edge: 640
    jpeg-quality: 0.82                # 起始质量
    min-jpeg-quality: 0.70            # 质量下限
    max-output-bytes: 1048576         # 压缩后 ≤ 1 MB
    daily-limit: 4                    # 每会员每日张数
    title-max-length: 200
    comment-max-length: 200
    comment-max-per-minute: 10        # 评论频率限制，0 表示不限制
```

> 说明：`max-output-bytes` / `daily-limit` / `need-review` 为业务硬规则，均从配置读取，改值无需改代码。生产可在 `application-prod.yml` 覆盖 `upload-dir` 与 `need-review`。

## 七、存储与部署（沿用 V1 单机方案）

```
/opt/fitness/upload/moments/2026/11/05/{uuid}.jpg        # 大图 ≤1MB
/opt/fitness/upload/moments/2026/11/05/{uuid}_thumb.jpg  # 缩略图 ≤150KB
```

- Nginx 已有 `location /upload/ { alias /opt/fitness/upload/; expires 7d; }`，无需新增配置。
- 文件名随机 UUID + 固定 `.jpg` 后缀，目录按日期分散，禁止目录穿越与目录列表。
- 静态目录禁止任何脚本解析（Nginx 不把 `/upload/` 交给后端或 PHP-FPM）。
- 备份：沿用每日 `tar` 打包 `/opt/fitness/upload` 同步异地；数据库 `mysqldump` 同频。
- 磁盘估算：4 张/人/日 × 20 人 ≈ 80 张/日 × 1.15 MB ≈ 92 MB/日，需按保留周期预估并加磁盘告警。

## 八、安全要点

1. **上传**：魔数 + 扩展名 + MIME 三重校验；限制像素总数；重编码去 EXIF；随机文件名；固定 `.jpg` 后缀。
2. **限额**：DB 原子计数 + 事务，不信前端额度；时区统一 `Asia/Shanghai`。
3. **评论**：纯文本、长度限制、前端转义渲染、后端过滤控制字符；软删保留结构。
4. **权限**：列表/详情/删除/审核逐接口校验身份与归属；教练不能发布、不能删他人图片。
5. **内容**：审核默认开启；驳回理由对作者可见；敏感操作（审核、删除）写 `operation_log`。
6. **隐私**：仅登录用户可见，无公开分享；图片不含 EXIF 定位信息。

## 十一、待确认事项

1. **是否需要管理员审核**？原型第 7 屏为可选；若希望发布即展示，把 `need-review` 设为 `false` 即可。
2. **教练/管理员能否发布**？当前设计为「仅会员」，符合「会员自我展示」定位。
3. **图片是否需要登录态鉴权**？当前为 Nginx 直出 + 随机 UUID；若要求严格「仅登录可见」，需改为后端 `/api/moments/files/{id}` 校验 token 后再吐流（多一层 IO，2C4G 仍可承受）。
4. **驳回是否返还额度**？当前口径为不返还（防刷屏）。
5. **是否需要点赞 / 消息提醒**？本期不做，评论回复不触发公众号通知。
6. **内容保留周期**？图片是否永久保留、是否按年归档清理，影响磁盘容量规划。

## 十三、实施补充：腾讯云图片审核 + 批量审核

> 2026-11-05 实施时追加，记录相对上文设计稿的新增与调整。

### 13.1 机审链路（逐张）

```
用户提交一张图
  → 前端 canvas 预压缩（长边 1920 / JPEG 0.82）
  → POST /api/moments/images（一次请求一张图）
  → 后端魔数校验 / 20 MB 拒绝 / 4000 万像素拒绝
  → 后端完整重压缩：长边 1920→1600→1280 × 质量 0.82→0.70，压缩后 ≤ 1 MB
  → 腾讯云天御 IMS ImageModeration 单图审核（一张一次调用）
  → Block / Review(可配) → 打回「当前这一张」：400 + 具体原因，不落库、不占额度
  → Pass / 未启用 / 异常放行 → 原子额度 + 落盘 + 落库
```

- 前端一次选多张时**串行逐张上传**，因此一张一张上传 = 一张一张机审；某张被打回只影响该张，发布页按图片卡片逐条展示结果。
- 腾讯云 `ImageModeration` 本身是单图接口，本期未引入批量审核 API；若后续要一次请求多图，只需替换 `ImageAuditService` 实现，业务层不动。

### 13.2 配置项（两个审核开关见 13.7；本节为 `app.moments.audit.*` 连接参数）

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `false` | **兼容别名**（旧版机审开关）；与顶层 `machine-audit-enabled` 任一为 `true` 即开启机审 |
| `endpoint` | `ims.tencentcloudapi.com` | 天御 IMS 接入点 |
| `region` | `ap-guangzhou` | 地域 |
| `version` / `action` | `2020-12-29` / `ImageModeration` | 接口版本与动作 |
| `secret-id` / `secret-key` | 空 | **TODO 填腾讯云 API 密钥**，建议环境变量覆盖，禁止提交仓库 |
| `biz-type` | 空 | 控制台创建的审核策略，可选 |
| `timeout-ms` | `5000` | 单次调用超时 |
| `fail-open` | `true` | 机审异常时放行并转人工；`false` 则拒绝上传 |
| `review-as-reject` | `false` | `Review`（疑似）时：`false` 转人工复核，`true` 直接打回 |

签名用 JDK `HttpClient` + TC3-HMAC-SHA256 自行实现，未引入腾讯云 SDK，依赖最轻、便于换服务商。

### 13.3 机审结论与落库

| Suggestion | `audit_status` | 图片 `status` | 前端提示 |
| --- | --- | --- | --- |
| `Pass` | `PASS` | 按 `need-review` 决定 | 机审通过 |
| `Review` | `REVIEW` | 强制 `PENDING` | 转人工复核 |
| `Block` | `BLOCK` | 不落库 | 「当前图片已被打回：xxx」 |
| 调用异常 | `ERROR` | 按 `fail-open` | 机审异常转人工 / 拒绝上传 |
| 未启用 | `SKIPPED` | 按 13.7 双开关组合决定 | 未进行机器审核 |

`media` 表新增 `audit_status / audit_suggestion / audit_label / audit_score / audit_request_id / audit_at / batch_id`，用于审计追溯与按批次定位被打回的那张。

### 13.4 管理端批量审核

- `POST /api/admin/moments/batch-review`：`{ ids, action: APPROVE|REJECT, reason }`
- **逐张独立处理**：某张状态不对、驳回未填理由等只记录该张失败原因，其余照常完成
- 返回 `{ total, successIds, failed: [{ id, reason }] }`，审核页明确展示「哪张没处理、为什么」
- 单张入口 `POST /api/admin/moments/{id}/review` 保留；审核动作写 `operation_log`

### 13.5 额度口径补充

- 机审打回 / 文件校验失败：**不落库、不占额度**（与原设计稿一致）
- 人工驳回、主动删除：**不返还额度**（与原设计稿一致）
- 原子计数用 `INSERT ... ON DUPLICATE KEY UPDATE` + 事务内读数，超额抛异常整体回滚

### 13.6 上线前待办

### 13.7 双审核开关（机审 / 人审独立可配）

两个开关彼此正交，改 `application.yml` 后重启即可生效，无需改代码：

| 配置项 | 层级 | 默认 | 作用 |
| --- | --- | --- | --- |
| `app.moments.machine-audit-enabled` | 顶层 | `false` | **开关① 机器审核**：开启后每张图片提交时调用腾讯云 IMS；关闭则完全跳过、不发 HTTP |
| `app.moments.need-review` | 顶层 | `true` | **开关② 人工审核**：开启后进待审核队列；关闭则不入队 |
| `app.moments.audit.enabled` | `audit.*` | `false` | 旧版机审开关的兼容别名，与开关①任一为 `true` 即开启；新配置只用开关① |
| `app.moments.enabled` | 顶层 | `true` | 风采功能总开关，与上面两个审核开关无关 |

四种组合（`MomentService.resolveInitialStatus()` 是唯一决策点）：

| 机审 | 人审 | 机审通过 / 跳过机审后 | 机审 Block | 机审 Review |
| --- | --- | --- | --- | --- |
| 开 | 开 | `PENDING`，管理员通过才展示 | 打回该张 | `PENDING` 待人工复核 |
| 开 | 关 | `APPROVED` 立即展示 | 打回该张 | `PENDING` 安全兜底 |
| 关 | 开 | `PENDING` 待人工 | 不适用 | 不适用 |
| **关** | **关** | **`APPROVED`，上传成功立即在风采广场展示** | 不适用 | 不适用 |

- 唯一例外：机审返回 `Review`（疑似）时，即使人审关闭也保留 `PENDING`；管理端审核接口始终可用，不会留下无人可审的死局。若希望疑似图直接打回，把 `app.moments.audit.review-as-reject` 设为 `true`，避免队列堆积。
- 两个开关都不影响压缩、每日 4 张额度、评论楼中楼；管理端批量审核接口与开关解耦，人审关闭后仍可处理历史 `PENDING`。
- 前端通过 `GET /api/moments/config` 读取 `ConfigVO(machineAuditEnabled, needReview, directPublish)`：发布页的流程说明、逐张结果文案与上传按钮随之变化；管理端审核页在人审关闭时显示提示条。
- 机审开启但未填密钥时输出**一条** WARN（只告警一次）并降级为 `SKIPPED`，不阻断上传；日志中不打印密钥。
- 机审关闭路径省去一次腾讯云 HTTPS 往返与 base64 编码，也缩短了上传事务的持锁时间。

> 上线前检查：确认两个开关的组合符合当前运营阶段，尤其**两关都关时图片未经任何审核即公开展示**，请配合内容合规约定使用。
