## 产品概述
在「会员风采」的图片发布流程中，把「机器审核」与「人工审核」做成两个彼此独立、可分别开启或关闭的配置开关，由管理员按运营阶段自行组合，无需改代码。

## 核心 Features
- **机审开关**：开启时每张图片提交即调用腾讯云图片审核；判定违规的那张单独打回并说明原因，同批其他图片不受影响；关闭时完全跳过机审。
- **人审开关**：开启时图片进入待审核队列，管理员（支持批量）通过后展示；关闭时不进入队列。
- **两关都关闭**：会员上传成功后图片立即在风采广场展示，无需任何等待与审核动作。
- **四种组合行为明确**：机审＋人审、仅机审、仅人审、都不开，各自的结果与用户可见文案一致。
- **开关状态可见**：发布页按当前组合显示准确的流程说明与上传结果文案；管理端审核页在人审关闭时给出明确提示。
- 每日 4 张额度、图片压缩、评论与楼中楼回复等既有规则不受开关影响。

## Implementation Approach

### 现状结论（已核实）
`MomentService.upload()` 的状态判定为 `props.isNeedReview() || AUDIT_REVIEW.equals(auditStatus) ? PENDING : APPROVED`，`app.moments.need-review` 与 `app.moments.audit.enabled` 两个配置项其实已存在，且「机审关＋人审关 → APPROVED」在数据链路上已可达成。但存在四处不一致，本轮逐一解决：
1. 两个开关层级不对称（一个顶层、一个藏在 `audit.*` 里），容易被误认为腾讯云 API 参数；
2. 机审开关与「密钥是否填写」耦合在 `TencentImageAuditServiceImpl.enabled()` 中，密钥缺失时静默关闭且不告警，运维不可感知；
3. 状态判定是一行三元表达式，四种组合没有单一、可测试的落点；
4. 前端发布页把 `SKIPPED` 写死为「转人工审核」、说明文案写死「每张图片独立审核」，管理端与生产文档也未体现双开关。

### 关键决策
- **顶层平级双开关**：新增 `app.moments.machine-audit-enabled`（机审）与既有 `app.moments.need-review`（人审）并列，`audit.*` 退化为纯 API 连接参数（endpoint / region / version / action / secret / biz-type / timeout / fail-open / review-as-reject）。`app.moments.enabled` 保持为「风采功能总开关」，注释中三者明确区分，避免混淆。
- **向后兼容**：`MomentProperties.Audit` 保留 `enabled` 字段作为兼容别名，在 `MomentProperties` 提供派生方法 `machineAuditOn()`，取 `machineAuditEnabled || audit.enabled`；旧配置仍可开启机审，Spring Boot 对未知属性默认忽略，不会启动失败。`needReview` 继续由 Lombok 生成 `isNeedReview()`。
- **密钥解耦**：`enabled()` 改为判断 `props.machineAuditOn()`；密钥缺失时 `log.warn` 一条可读告警（不打印密钥、不刷屏，避免每次上传重复刷屏可仅在调用点告警），返回 `SKIPPED` 降级，不再静默。
- **状态决策集中**：在 `MomentService` 抽出 `resolveInitialStatus(String auditStatus)`，把四种组合收敛到一处并配注释表；`BLOCK` 打回、`ERROR` 按 `fail-open` 的既有判断保持不变。

| 机审 | 人审 | 机审 PASS/SKIPPED 后 | 机审 BLOCK | 机审 REVIEW |
| --- | --- | --- | --- | --- |
| 开 | 开 | `PENDING`，管理员通过才展示 | 打回该张 | `PENDING` 待复核；`review-as-reject=true` 时打回 |
| 开 | 关 | `APPROVED`，立即展示 | 打回该张 | 仍 `PENDING` 兜底（管理端审核接口始终可用，不留无人可审死局） |
| 关 | 开 | `PENDING` 待人工 | 不适用 | 不适用 |
| 关 | 关 | **`APPROVED`，上传即展示** | 不适用 | 不适用 |

> 机审疑似（REVIEW）在人审关闭时仍进 `PENDING` 属安全兜底，是唯一不直接展示的例外；文档需写明，建议此组合配 `review-as-reject: true` 直接打回，避免队列堆积。

- **配置暴露给前端**：新增 `GET /api/moments/config` 返回 `ConfigVO(machineAuditEnabled, needReview, directPublish)`，而不是往 `QuotaVO` 里塞字段。理由：`QuotaVO` 是额度语义，混入开关违反单一职责；新接口为纯内存读配置、无 DB 查询、无密钥与 PII，可安全复用现有 `/api/**` 鉴权；会员端与管理端都能复用，未来加开关不需要改额度 record。前端发布页用 `Promise.all` 并行取 quota 与 config，多一次轻量 GET，性能可忽略。
- **不重构审核在事务内的网络调用**：`upload()` 上的 `@Transactional` 包着机审 HTTP 请求是既有实现，本轮不扩大改造范围；但机审关闭时 `audit()` 立即返回 `SKIPPED`、不发起 HTTP（默认 5s 超时），客观上缩短了「两关都关」路径的事务持锁时间，这是本轮主要性能收益。

### 性能与复杂度
- 全部改动为 O(1) 配置读取与一次布尔判断，不新增 DB 查询、不新增循环、不新增前端轮询。
- 机审关闭路径省去一次腾讯云 HTTPS 往返与 base64 编码，是最直接的热点优化；机审开启路径耗时不变（单次 `ImageModeration`，受 `timeout-ms` 约束）。
- `ConfigVO` 无状态对象，接口可安全幂等调用。

## Implementation Notes
- 复用既有模式：`@ConfigurationProperties` + Lombok `@Data`、`Result.ok(...)`、`@RequiredArgsConstructor` 注入、`request<any>(path)` 前端封装、`toast` 提示；不引入新架构、新状态管理库。
- 日志：密钥缺失用 `log.warn` 输出「已开启机审但未配置密钥，本张图片降级为人工/直接发布」这类可行动信息；严禁打印 `secret-id`、`secret-key`、图片 base64 或完整响应体；避免每图重复刷屏。
- Blast radius 控制：不改 `compress()`、`quotaMapper.consume`、`comments()`、`reviewOne()`/`batchReview()`、`MediaVO` 与数据库结构；`reviewOne()` 保持可用，人审关闭后历史 `PENDING` 仍能被管理员处理。
- 前端文案只做条件渲染，不改动 `precompressImage`、逐张串行上传循环与「打回某张」的结果处理逻辑；保留 `requestForm` 的错误原因透传。
- 生产配置用环境变量注入密钥，不写入仓库；本轮仅同步文档中的占位配置。
- 不执行 git 提交，不改动与审核开关无关的代码。

## Architecture Design
改动沿现有分层纵向贯通，无新增组件与跨层调用：

```
application.yml / application-prod.yml（两个开关）
   -> MomentProperties（machineAuditOn / isNeedReview）
      -> TencentImageAuditServiceImpl.enabled()  决定「是否调用腾讯云」
      -> MomentService.upload() -> resolveInitialStatus()  决定 PENDING / APPROVED
      -> MomentController  /api/moments/config  -> ConfigVO
         -> PublishView（发布说明、逐张结果文案）
         -> MomentReviewView（人审关闭提示）
```

机审开关只影响「是否发起第三方调用」，人审开关只影响「落库初始状态」，两者正交；`AUDIT_REVIEW` 作为安全兜底横跨两者。管理端批量审核接口与开关解耦，始终可用。
